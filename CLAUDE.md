## Two systems live in this repo: the thesis pipeline (above) and B-SMART

Scope rule: B-SMART is an extensible framework, but its first validated domain is
pharmacy retail. The target design uses a pooled, de-identified multi-pharmacy
domain model plus shop-specific operational data and owner-entered constraints.
Continuous operation means event/scheduled inference and monitored periodic
retraining; never retrain blindly on every transaction. Keep implemented
prototype features visibly separate from proposed pharmacy extensions.

The numbered scripts above are the original static thesis pipeline — synthetic
CSV in, pickles out, `predict.py`/`api/routes.py` serve them read-only. Alongside
it, a second, actively-developed system ("B-SMART") has grown up: a real
multi-tenant operational app (SQL-backed CRUD for orgs/branches/products/sales/
inventory/payments/etc.) plus its own leak-free real-data ML pipeline. **Both
mount into the same FastAPI app (`api/main.py`) and run side by side** — they
share no data model yet, only a CSV schema handshake (see below). Read
`docs/THESIS_PRODUCT_MASTER_PLAN.md`, `docs/FEATURE_STATUS.md`, and
`docs/REAL_DATA_PROTOCOL.md` before touching either the schema or the ML
research-question framing; they are the source of truth for B-SMART, not this
file.

### The anonymous Upload flow has a second, genuinely dynamic model too

`/api/upload/{token}/score` (`upload_service.score_upload`) still scores
against the fixed `churn_model.pkl` — trained once on the synthetic thesis
dataset, never retrained. That's intentional for that number (see the module
docstring), but it means a stranger's uploaded file is only ever *scored*,
never used to train anything, which understates what this codebase can
actually do with arbitrary data.

`/api/upload/{token}/train-churn` (`upload_service.train_dynamic_churn`)
closes that gap: it adapts the uploaded file's four columns into the
canonical schema (`upload_service._to_canonical_frame` — one invoice per
row, since the loose upload format can't express multi-line invoices) and
runs it through the *same* `ml.real_pipeline.train_churn` a B-SMART business
uses, fitting a brand-new model on nothing but that file and returning its
own chronological hold-out PR-AUC/ROC-AUC/Brier/lift. Nothing is persisted —
a one-off upload session has no organization to save an artifact under, so
the model is discarded after scoring; only the honest metrics survive.
Wired into `Upload.jsx`'s results step as "নিজের ডেটা দিয়ে নতুন মডেল ট্রেন
করুন", verified end-to-end with a synthetic file with genuine churn/retain
variation (ROC-AUC 0.897, PR-AUC 0.957 on that specific file — not fixed
numbers, whatever the uploaded data produces).

`segments_for` and `forecast_for` in the same module were *already* dynamic
(K-Means re-fit and seasonal-naive computed fresh per upload) — only churn
scoring was still static before this.

The bridge between the two systems is the CSV schema: `data_import_routes.py`
exports operational sales in exactly the columns `ml/real_pipeline.py` requires
(`branch_id, invoice_id, line_id, sold_at, customer_pseudo_id, sku, quantity,
unit_price, discount_amount, line_total`). There is no automatic hookup yet —
running the real pipeline on live tenant data is a manual export → train step.

`frontend/src/pages/Upload.jsx` intentionally still calls the *old* pickle-era
`/api/upload*` endpoints (`api/routes.py`) — that page is a one-off scoring
pass against the thesis pickles for a visitor with no account, and never
touches the DB. Real, org-owned sales history intake is a separate feature:
`api/data_import_routes.py`'s `/api/app/imports` → `/api/app/imports/{id}/
validate-sales` → `/api/app/datasets/sales.csv` flow now has both `api.js`
functions (`importSalesFile`, `validateSalesImport`, `exportSalesDataset`) and
a UI section ("প্রকৃত বিক্রয় ইতিহাস আমদানি") on `BusinessSetup.jsx`, gated on
having an active organization. Smoke-tested end to end with curl: upload →
validate correctly flags SKUs not yet in the org's product catalog.

**Accounts and roles (2026-09-28).** Email + password sign-in now exists:

### Bring-your-own-data

`/upload` takes any transaction CSV/Excel, asks the user to map four columns
(customer id, date, amount, quantity), rebuilds RFM features, and ranks customers
by churn risk with a downloadable CSV. `upload_service.py` never opens a pickle —
it calls `predict.py`, same as the route handlers.

**It scores, it never retrains.** Nothing under `output/` is written by the
serving layer, so the thesis numbers cannot drift from a dashboard visit.

Two definitions necessarily differ from `01b_customer_features.py`, because an
uploaded file has no `Days_Since_Last_Purchase` or `Purchase_Frequency_Monthly`
column to average: recency is derived from the newest date in the file, and
frequency from transactions per active month. On the legacy dataset this
degradation was measured (ROC-AUC ≈ 0.77 against that dataset's 0.722
headline) — **that measurement has NOT been repeated on the pharmacy dataset
and is stale**; `churn_model.pkl` is now retrained on pharmacy data whose own
headline is 0.924, so the upload-path gap is currently unquantified. The
constants are in `upload_service.py`; **re-measure with complete customer
histories** — a truncated row slice cuts each customer's last purchase and
reports a badly degraded figure for reasons unrelated to the model.

Percentages from an upload are *not* calibrated for a business outside the
training data. The response carries a `domain_warning` and the UI renders it;
the `90+ days inactive` column is the dependable one, since it is measured from
the user's own dates rather than predicted.

### Partial payloads use the median, not zero

`predict._vectorise` fills an absent feature with the **population median**.
Filling with 0.0 is not neutral — the MinMax scalers were fit on training data
whose minimum is above zero for most features, so a raw 0.0 scales negative and
lands outside anything the model saw. Symptom when this was wrong: a four-field
churn payload returned 0.93 no matter what those fields said, and every customer
in an uploaded file came back "High" risk. If a prediction looks suspiciously
uniform, check the fill value first.

## Python environment

`.venv312/` (Python 3.12) — TensorFlow has no build for the system's Python 3.14.
Activate once, then everything is plain `python`:

```powershell
.\.venv312\Scripts\Activate.ps1   # PowerShell
python run_all.py

```

**No environment variables are required.** `utf8_console.py` is imported first by
every script that prints, and reconfigures stdout/stderr to UTF-8. Adding a new
script that prints `→ ✓ ⚠`? Add `import utf8_console  # noqa: F401` above the other
imports, or it will die with `UnicodeEncodeError` on a cp1252 console.

Never document `PYTHONIOENCODING=utf-8 ...` or any `VAR=value cmd` form — this user
is on PowerShell, where that is parsed as a command name and fails.

## Fixed: the fabricated-forecast trap

`04_forecasting.py` used to fall back to `actual + np.random.normal(...)` when
TensorFlow or statsmodels was missing, silently producing fake results (MAPE 0.74%).
Both fallbacks are now removed — the script raises `SystemExit` with install
instructions instead. A missing dependency can no longer look like a finding.

Verify a run was real by checking `output/models/lstm_model.h5` and
`output/figures/lstm_training_loss.png` exist.

## Conventions

- Run from the repo root — every path is relative (`output/...`), so CWD matters.
- Matplotlib is `Agg`-backed; figures go to `output/figures/` at 300 DPI, never `plt.show()`.
- Palette used across figures: `#0A8754` green, `#0D1B2A` navy, `#E63946` red, `#64748B` grey.
- `random_state=42` everywhere. Keep it — thesis numbers must reproduce.
- Intermediate state is passed via `pickle`, not re-computed.
- CSVs are written `encoding="utf-8-sig"` (Excel-friendly, BOM on the header).
- Amounts are BDT; the currency suffix `_BDT` is part of the column names.

## Current results — Bangladesh-pharmacy dataset, full pipeline rerun 2026-09-12

**These are the numbers to cite.** Every stage (`02` … `10`, plus `13`) was
rerun on the dataset built by `00a_generate_pharmacy_dataset.py`. Nothing from
the deleted legacy multi-sector dataset survives in `output/`.

**Classification — segment / CRM tier.** The label is the shop's manually
maintained CRM tier: it tracks customer value but carries perception noise and
~18% stale tags (see `normalized_data/DATASET_MANIFEST.md`), so it is a
genuinely hard 4-class problem, not a lookup.

| Run | Model | Accuracy |
|---|---|---|
| `02` v1 — transaction-level, CLV included (**leaky**) | XGBoost | 85.29% |
| `02b` v2 — customer-level, no CLV (**honest**) | Random Forest | **51.55%** |
| `02b` v2 | Logistic Regression | 49.93% |
| `02b` v2 | XGBoost | 46.68% |
| `09` untouched holdout | XGBoost (selected on dev CV) | 47.78% [44.6, 50.9] |

Majority baseline is 35.14%. McNemar XGBoost vs Random Forest: **p = 0.007,
significant** — unlike the legacy run, model choice genuinely matters here.

Note the same selection-discipline point as the forecasting result: on the
`09` holdout, Extra Trees (46.67%) and Random Forest (46.23%) sit below the
selected XGBoost (47.78%), and XGBoost was chosen on development CV (48.89%)
*before* the holdout was opened. Report the pre-registered choice.

**Leakage ablation:** 85.29% (transaction-level + CLV) → ~51% (customer-level,
no CLV). Roughly 34 points of the headline accuracy came from leakage, not
from modelling.

**Forecasting** (`04_forecasting.py`, monthly sales):

| Model | RMSE | MAE | MAPE |
|---|---|---|---|
| **Seasonal-naive** | **11,821** | **7,896** | **4.08%** |
| LSTM | 18,928 | 16,420 | 9.55% |
| ARIMA(2,1,2) | 32,191 | 27,349 | 16.16% |

`10_retrain_forecasting.py` rolling-origin selection agrees: it picks
**`seasonal_naive`** (development CV WAPE 5.62%, next best `ets_add` 5.96%),
holdout WAPE 4.11%. "Same month last year" beats both the deep and the
statistical model — state this plainly, it is the strongest evidence that the
series is seasonal. LSTM drifts slightly between runs (EarlyStopping epoch);
ARIMA and seasonal-naive are deterministic.

On the holdout `ets_add` edges seasonal-naive (WAPE 4.073% vs 4.106%), but
seasonal-naive won the development CV and was selected before the holdout was
opened — report the pre-registered choice, not the post-hoc winner.

**Clustering:** K=4, silhouette **0.2354**. `OPTIMAL_K = 4` is still a business
choice ([03_clustering.py:119](03_clustering.py#L119)), not the metric's pick.

**Churn** (`09_retrain_models.py`, untouched holdout, base rate 34.3%):
ROC-AUC **0.936**, PR-AUC **0.820**, **2.47x lift @10%**.
`08_churn_prediction.py` agrees (RF: ROC-AUC 0.911, PR-AUC 0.775, 2.34x).
Higher than the legacy dataset's 0.722 — chronic-medication customers refill on
a regular cadence, so a lapse is genuinely more detectable in pharmacy data
than in mixed retail. `Recency`, `RFM_Score` and `CLV` are excluded as
label-derived.

**Returns** (`09_retrain_models.py`, group-disjoint holdout, base rate 4.8%):
ROC-AUC **0.530**, PR-AUC **0.064** vs 0.048 random.
**A negative result — report it as one.** Returns remain near-random with
respect to pre-dispatch features, reproducing the legacy finding.

**B-SMART Algorithm 1** (`13_bsmart_recommendation_engine.py`, full 13-constraint
engine): 2,448 candidates → 564 feasible → R_t of 15, balanced 5 reorder /
5 near-expiry / 5 retention. Full record in `docs/BSMART_ALGORITHM_RESULTS.md`
— cite that file, do not re-derive from the JSON.

> On the legacy dataset an early return model scored ROC-AUC 0.97 because
> `Customer_Satisfaction_Score` was in the feature set — a score given *after* the
> purchase experience, so a consequence of the return, not a predictor. Same family
> of bug as the CLV leak. The rule stands on any dataset: when a binary model looks
> great, check for post-outcome features first.

Silhouette still favours a smaller K than the one deployed: on the RFM features it
peaks at K=2 (0.4631) versus K=4 (0.3994), and `03_clustering.py`'s own feature set
reports 0.2354 at K=4. `OPTIMAL_K = 4` is hardcoded
([03_clustering.py:119](03_clustering.py#L119)) — defensible as a business choice
(Low/Moderate/High/VIP are actionable), but say plainly that it is not what the
metric selected.
